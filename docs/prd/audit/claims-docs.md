## Mechanics (origin/master 712b125)

> **Note:** this describes 712b125. PR #26, merged 2026-10-06 after the audit, records no-provider chat jobs as `failed`, adds `POST /api/cron/maintenance` (job/command/provider reaper, every 5 min) and fixes the report's models and live-node lines.

### M1. How jobs get assigned, and what happens to `model: "gpt-4o-mini"`

1. **Entry points.** `POST /api/chat` (apps/web/app/api/chat/route.js:59) and `POST /v1/chat/completions` (apps/web/app/v1/chat/completions/route.js:93) both call `createChatJob()` (apps/web/lib/data/chat.js:206). This is the **only** code path that creates jobs; the only `jobs` insert is chat.js:275. No generic job-submission API exists, and `/api/jobs` is GET only.
2. **Push assignment, done once at creation.** `pickChatProvider()` (chat.js:37-89) selects providers with `status='available'` AND `last_seen` within 2 min (:44-45). If a model is named, it keeps only providers whose `specs.served_models` **exactly** contains the string (:67-72). It drops `private` tier, providers below `min_trust_tier`, and saturated nodes (active_jobs ≥ cap, or GPU ≥ 95%). From the rest it makes a weighted random pick: reputation × tokens/s × headroom (:128-172).
3. **Status at insert** (chat.js:258): a provider was found → `assigned` with provider_id set. Otherwise, if `NVIDIA_NIM_API_KEY` is set → `running` with `input_spec.fallback='nvidia-nim'`, and the SSE handler streams from NIM. Otherwise → **`pending` with provider_id NULL**.
4. **Daemon side.** Daemons poll `/api/v1/node/jobs/poll` every 15 s (start.js:1509). The server returns only rows where `provider_id = <this provider> AND status = 'assigned'` (node-api.js:254-260). Nothing ever claims an unassigned `pending` job. There is no pull or claim queue, and no re-assignment.
5. **"gpt-4o-mini" with no NIM key.** No provider advertises that string; served_models are Ollama tags or vLLM served names (register.js:204), and nothing maps OpenAI model names. So `source='none'`, and **the row is still inserted as `pending`** before the route returns 503 (completions/route.js:104-106; api/chat/route.js:75). The job **stays `pending` forever.** Master has no timeout, expiry, reaper, pg_cron or scheduled job (`grep -rn "pg_cron|cron.schedule|reap|expire"` finds nothing relevant, and no `.github/workflows` file has a `schedule:`). Every such request adds one permanent row to the "Jobs pending" count.
6. **"gpt-4o-mini" with NIM configured.** The job is created `running` with model_name `gpt-4o-mini`. runNimFallback passes `job.model_name` to NIM (chat-stream.js:143), which rejects the unknown model, and the job is finalized `failed` (chat-stream.js:190-197). If the client never opens the stream, which is possible with /api/chat since streaming happens on a later GET, the job stays `running` forever.
7. **Other ways a job gets stuck.** An `assigned` job whose daemon dies stays `assigned` forever: there is no lease or timeout, and the poll keeps returning it only to that provider. The daemon never moves a job to `running`; it goes straight from `assigned` to `completed`/`failed` (start.js:467-508). The SSE consumer gives up after 10 min (chat-stream.js:28, 101-109) but does not update the job row.
8. **Distributed flag bug.** `distributed: true` still goes through the single-provider pick. If no single provider serves the model and NIM is off, /api/chat returns 503 before the RPC proxy (stream route:84-96) can run. If a single provider *is* picked, that daemon also executes the job, because it has no `distributed` check (grep in apps/cli finds none), while the stream route proxies to the RPC primary.

### M2. What populates `models`, and why it is empty while providers exist

- `public.models` is created in 20260312000000_initial_infernet_schema.sql:41-48 with `visibility default 'private'`. The only data that ever went in was demo seeds, and 20260428000000_drop_demo_seeds.sql:50-58 deletes them.
- **Nothing in the code writes to `models`.** The only references are reads: lib/data/infernet.js:247 (`/api/models`) and chat.js:363 (a fallback). Heartbeat, register, seeds and tooling never write it.
- Real model availability lives in `providers.specs.served_models`, refreshed on register (sanitized, node-api.js:22-26) and on every heartbeat (raw, node-api.js:235-237). `/v1/models` reads served_models from providers seen in the last 10 min and falls back to `models` only if none are found (chat.js:340-369).
- So "Models: 0" in the daily report means "catalog table never populated". It does not mean no models are served. Separately, served_models can be empty on a live node. Ollama models are listed only if `config.engine.ollamaHost` is set (register.js:168: `ollamaHost ? detectOllamaModels(...) : []`). A node set up without that key advertises nothing, and is then picked only for requests that name no model.

### M3. node_commands lifecycle

- **Create.** Only the owner, from the dashboard: `POST /api/v1/user/nodes/[pubkey]/commands` (route.js:34-104). It needs a Supabase session or CLI bearer plus `pubkey_links` ownership (`userOwnsPubkey`, node-commands.js:21-31). The verbs are `model_install | model_remove | train_shard` (:10). The row is inserted `pending` (:37-61).
- **Claim.** The daemon polls `/api/v1/node/commands/poll` every max(2 × poll, 30 s) = 30 s (start.js:1515-1520). pollCommandsForNode does a guarded `pending → running` update with started_at (node-commands.js:139-165).
- **Execute** (start.js:623-745). `model_install` takes the vLLM path when vLLM is installed and an `hf` repo is given: download → start vLLM → wait up to `VLLM_INSTALL_TIMEOUT_S` (default 600 s), posting progress via `/progress`. Otherwise it fit-checks and runs `ollama pull` with progress. `model_remove` runs `ollama rm`. `train_shard` downloads the shard and runs the Unsloth LoRA script.
- **Ack.** `/commands/[id]/complete` with `completed` or `failed`. This is accepted only while the row is still `running` and the pubkey matches (node-commands.js:172-220). Cancel sets `cancelled`, and the daemon notices through the progress response (node-commands.js:69-109, 271-274).
- **What makes them fail.** Any throw in runNodeCommand: an `hf:` model on a node without vLLM, the fit check failing, ollama exiting non-zero or missing, vLLM not serving within the timeout (with a vllm.log tail), a shard fetch HTTP error, unsloth exiting non-zero, or an unknown verb (start.js:705-743).
- **Timeouts and reaper.** Master has **none** on the server. A command for an offline node stays `pending` forever. A daemon that crashes mid-install leaves the row `running` forever. Commands are run serially inside the poll tick (start.js:552-554), so a long pull blocks later commands. The only timeout is the vLLM wait on the node.

### M4. CPR receipts

- **Writer.** Every `POST /api/v1/node/jobs/[id]/complete` builds a receipt: `buildReceiptBody`, apps/web/lib/cpr/receipts.js:105-133, called from node-api.js:327-348. It is inserted into `cpr_receipts_queue` as `pending` and flushed immediately (queue.js:22-74). NIM-fallback jobs and RPC-proxied jobs complete elsewhere (chat-stream.js finalizeJob, stream route) and **emit no receipt**.
- **Receipt quality.** Receipts are unsigned, despite the "platform sig" comment. `amount` is always 0 for chat. `job.type` is undefined because the complete handler selects only `id, provider_id, payment_offer, payment_coin, status` (node-api.js:281), so every category falls back to "inference". buyer_did is a job-id placeholder.
- **Config.** `CPR_ISSUER_API_KEY` is required; `CPR_API_BASE_URL` defaults to https://coinpayportal.com/api/reputation (cpr-client.js:24-36). **Without the key, `tryFlushReceipt` returns `pending` without bumping attempts** (queue.js:43-46). Rows therefore stay `pending` forever and are never marked failed.
- **"sent"** means CoinPay's `POST {base}/receipt` returned HTTP 2xx (cpr-client.js:47-95, `classifyResult`). 408, 429 and 5xx (and network errors) back off exponentially from 30 s and become `failed` after 8 attempts, about 64 min (queue.js:14-20, 84-103). Other 4xx become `permanent_fail`.
- **`/api/cron/cpr`** (apps/web/app/api/cron/cpr/route.js) accepts GET or POST with `Authorization: Bearer $CRON_SECRET` and returns 401 if CRON_SECRET is unset. It drains up to 25 rows where status is `pending` and next_attempt_at ≤ now (queue-drain.js:142-186).
- **Scheduling.** **Nothing in the repo schedules it.** There is no workflow `schedule:`, no vercel.json, no pg_cron, and railway.toml has no cron. The route's own comment says to "hit on a schedule (Vercel Cron, Supabase pg_cron, GitHub Actions…)". Retries only happen if some external cron exists.
- **Daily report labels.** "CPR Failed (retrying)" is mislabeled. Status `failed` means retries are exhausted and the row is terminal. Rows still retrying are counted under `pending` (daily-stats.js:129, 262).
- **Reputation.** No CPR data flows back into `providers.reputation`; nothing writes that column.

### M5. Payments

- **Invoice.** `POST /api/payments/invoice {jobId, coin, network?}` (payments/invoice/route.js) validates the coin against packages/config/payment-coins.js, reads `jobs.payment_offer`, calls `createInvoice` (packages/payments/src/coinpayportal.js:175-226), sets `jobs.payment_status='invoiced'`, and inserts an inbound `payment_transactions` row with status `pending` (:97-114). It has **no auth** and **no caller** anywhere in the web UI, SDK or CLI (`grep payments/invoice` finds only the route).
- **Gateway correctness is unverified and likely wrong.** coinpayportal.js:8-11 says the API shape "is not verifiable from this sandbox". It uses `https://api.coinpayportal.com/v1` + `/invoices` + `x-api-key`, with webhook header `x-cpp-signature` HMAC-SHA256 (:31-46, 249-290). The repo's working CoinPay integration (the .github/workflows/coinpay.yml bot) uses `https://coinpayportal.com` plus a business id.
- **Webhook.** `POST /api/payments/webhook` verifies the HMAC using `COINPAYPORTAL_WEBHOOK_SECRET`; if that is unset, it throws and returns 500. It then updates `payment_transactions` by invoice_id and mirrors `jobs.payment_status` (`confirmed`/`failed`/`pending`, not "paid").
- **Config.** `COINPAYPORTAL_API_KEY` (required), `COINPAYPORTAL_WEBHOOK_SECRET` (required for the webhook), optionally `COINPAYPORTAL_API_BASE_URL`, and `NEXT_PUBLIC_APP_URL` for the callback URL. railway.toml marks the CoinPay keys "(optional)".
- **Who writes `payment_transactions`.** (a) The invoice route (inbound). (b) The node complete handler (outbound, `address:'pending-payout'`), but only if `payment_offer > 0` (node-api.js:301-320). Chat jobs are created with `payment_offer: 0` (chat.js:267). **On master, real traffic never produces a payment row**; the count moves only if someone calls the unauthenticated invoice route by hand.
- **Billing on inference.** **None.** /api/chat and /v1/chat/completions need no account or API key, never check a balance or payment, and price everything at 0. The only limit is an in-memory 20 req/hr/IP (api/chat/route.js:10; completions/route.js:30). Dispatch is not payment-gated, and no payout sender exists (provider_payouts is only an address book).

### M6. Distributed inference and training

- **`distributed_jobs` / `node_roles`.** Created in 20260419000000_cli_support_and_payments.sql:94-129. **Never written or read by app code**; only daily-stats.js:121-122 counts them, so the report's "Distributed jobs" is structurally 0.
- **Real distributed path (IPIP-0033, llama.cpp RPC).** Flow: /chat "distribute" toggle → `jobs.input_spec.distributed=true` → stream route runRpcProxy picks an RPC primary (`specs.rpc_primary.models`) and at least 2 slices (`specs.rpc.models`), and fails closed otherwise → POSTs to the primary daemon's `http://address:port/v1/rpc/inference` (start.js:921-937), which runs llama-server with `--rpc`. This needs a primary with an inbound-reachable address/port and operators running `infernet inference primary` or `serve --backend rpc`. It is tracked only as a normal `jobs` row, never in distributed_jobs. /api/v1/rpc/census reports readiness. See M1.8 for the 503 gating bug.
- **Training market (IPIP-0030).**
  - Tables `training_jobs` and `training_shards` (20260501170000_training_market.sql).
  - **Create:** `POST /api/v1/training/jobs`, user-authed. The submitter must host the dataset at `dataset_base_url/shard-N.jsonl` (training/jobs/route.js:16-38).
  - **Claim and report:** `/api/v1/training/shards/available`, `[id]/claim`, `[id]/report` (signed).
  - **Executor:** the daemon polls every 60 s, **only if the operator opted in** with `INFERNET_ACCEPT_TRAINING=1` or `engine.acceptTraining` (start.js:1528-1540). It runs the Unsloth LoRA script with python3 (start.js:860-900).
  - So it can run end to end, but it needs an opted-in node with python3 + Unsloth + a GPU, plus a self-hosted dataset.
  - **Gaps.** No payment on shard completion (price_per_shard_usd is stored only). No adapter merge or aggregation. The job is marked `completed` even when every shard failed (training-market.js:186-197). No reclaim of shards claimed by dead nodes. The `@infernetprotocol/training` package (DeepSpeed/OpenRLHF/OpenDiLoCo/Petals) is imported by nothing.

## Biggest gaps (top 10)

1. **No billing or payouts on inference.** Every chat job is created with `payment_offer: 0` (chat.js:267). /v1/chat/completions needs no API key and reports `usage` 0 (completions/route.js:213), and dispatch is never payment-gated. Outbound payment rows are written only when payment_offer > 0 (node-api.js:303), so real traffic never writes one. No payout sender exists; provider_payouts is only an address book. Lightning, escrow, the fee, pricing and budgets are all missing.
2. **The CoinPayPortal gateway is a guess.** packages/payments/src/coinpayportal.js:8-11 says the API "is not verifiable from this sandbox". It uses `api.coinpayportal.com/v1/invoices` + `x-api-key` + `x-cpp-signature`, which does not match the repo's working CoinPay bot (coinpayportal.com + business id). The invoice route has no auth and no caller.
3. **Unservable requests become permanent `pending` rows.** For example, `model: "gpt-4o-mini"` with no NIM key: chat.js:258 inserts `pending` with provider_id NULL, then the route returns 503. Daemons poll only jobs `assigned` to them (node-api.js:257-258). Master has no reaper for jobs, node_commands or stale `available` providers. Fixed by PR #26 (reaper + no_provider failures).
4. **The `models` table is never written** (only demo seeds, deleted in 20260428000000). The report's "Models 0" is structural. Served models live in providers.specs.served_models, which needs `engine.ollamaHost` to be set (register.js:168).
5. **The daily report misleads.**
   - "Available" means status='available', which a crashed daemon keeps forever.
   - "Distributed jobs" counts a table nothing writes.
   - "CPR Failed (retrying)" counts terminal rows.
   - "Running" only ever counts NIM jobs, because the daemon never sets running.
6. **CPR receipts are mostly inert.**
   - They are unsigned and carry amount 0 and type 'inference'.
   - Without CPR_ISSUER_API_KEY they stay `pending` forever.
   - Nothing in the repo schedules /api/cron/cpr.
   - NIM and RPC jobs emit no receipt.
   - Nothing feeds back into `providers.reputation`, which nothing writes, so reputation routing is flat. IPIP-0007 is still marked Final.
7. **IPIPs marked Final have no code.**
   - 0013: batch `/api/v1/jobs/batch` + BullMQ, also advertised in the README and FAQ.
   - 0014: idempotency, reassignment, circuit breakers.
   - 0005: mobile talks to Supabase directly.
   - Petals (B.5) is still advertised in the README although IPIP-0031 is Replaced.
8. **The c0mpute substrate is claimed but absent.** The README, PROTOCOL, ARCHITECTURE and book say discovery and auctions run over c0mpute libp2p/gossipsub. Infernet has no such code, the daemon's census returns empty peers (start.js:1118-1129), and the c0mpute plugin installer is not in the repo.
9. **Distributed and training paths have real bugs.**
   - Distributed RPC mode is 503-gated by the single-provider pick (chat.js:241-258; api/chat/route.js:75), and the picked single provider also runs the job.
   - `distributed_jobs` and `node_roles` are dead tables.
   - Training shard adapter uploads fail: the upload URL is built over a base that already has `?token=` (training-market.js:58 vs start.js:1169).
   - There is no shard payment, no adapter merge, and jobs are marked completed even when every shard failed.
   - `@infernetprotocol/training` (DeepSpeed/OpenRLHF/DiLoCo/Petals) is imported by nothing, and the Mojo engine emits canned tokens.
10. **The privacy and security claims overstate.**
    - Heartbeat specs are stored unsanitized: `patch.specs = body.specs` at node-api.js:236 stores CPU, RAM totals, load and interconnects, contradicting the README's privacy claim.
    - E2E (NIP-44) covers the prompt only; responses return in plaintext.
    - No TEE or attestation, no Docker sandbox for jobs, and the secret-detection module is unused.
    - At-rest encryption is off unless INFERNET_DB_ENCRYPTION_KEY is set.
    - The book's consumer API (`/api/v1/jobs`, API keys) and the CONSUMER/PROVIDER docs (Nostr sign-up, `infernet/node` image, app./docs. subdomains) describe things that do not exist.
    - ARCHITECTURE.md still says the CLI holds a Supabase service-role key.
