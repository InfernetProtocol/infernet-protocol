## Abstract

Adds end-to-end encryption of chat prompts and responses between the
consumer (browser or CLI client) and the provider node, using
**NIP-44** (ECDH key agreement over secp256k1 + ChaCha20-Poly1305).
Both sides already hold secp256k1 Nostr keypairs. The consumer derives
a shared secret from their private key and the provider's public key;
the provider derives the same shared secret in the other direction.
Supabase, the Infernet control plane, and anyone observing the network
see only ciphertext. The provider decrypts to run inference and
re-encrypts each response chunk for the consumer.

Encryption overhead is microseconds per message (ChaCha20 is a
stream cipher designed for high-throughput software). Unlike Tor
(which is slow due to multi-hop routing, not encryption), this adds
no network hops and negligible latency.

The provider still reads plaintext during inference — that is
unavoidable without TEE hardware (IPIP-0026 Phase 3). This IPIP
protects content from every party **except** the assigned provider.

## Motivation

IPIP-0025 encrypts content at rest in Supabase using a server-side
key. The Infernet control plane operator can still read prompts
because they hold `INFERNET_DB_ENCRYPTION_KEY`. IPIP-0026 Phase 1
warns users about accidental secret exposure but doesn't protect
against a determined observer on the control plane.

This IPIP closes the gap: after it is implemented, the Infernet
control plane operator cannot read conversation content even if they
wanted to. Only the consumer and the assigned provider hold the
shared secret.

This is the same model used by Signal (ECDH + symmetric encryption),
Nostr DMs (NIP-44), and WhatsApp (Signal Protocol) — not Tor.
Tor's privacy goal is metadata hiding (who talks to whom). This
IPIP's goal is content hiding (what was said). They are complementary
and can be combined, but this IPIP does not add routing hops.

## Specification

### 1. Key material

Both parties use secp256k1 keys that already exist in the protocol:

| Party | Key | Where it lives |
|---|---|---|
| Provider | Nostr keypair (`node.privateKey` / `node.publicKey`) | Daemon config, advertised in heartbeat |
| CLI client | Nostr keypair from `~/.config/infernet/config.json` | Already exists (IPIP-0003) |
| Browser client | Ephemeral secp256k1 keypair generated per session | Browser `sessionStorage` only; never sent to server |

Browser ephemeral keys MUST be generated using `window.crypto.subtle`
with `{ name: "ECDH", namedCurve: "P-256" }` OR using a secp256k1
library (e.g. `@noble/secp256k1`) to match the Nostr key format.
For NIP-44 compatibility, secp256k1 is REQUIRED (not P-256).

### 2. Shared secret derivation (NIP-44 §2)

```
shared_secret = ECDH(consumer_privkey, provider_pubkey)
              = ECDH(provider_privkey, consumer_pubkey)
              // both sides compute the same value

conversation_key = HKDF-SHA256(
  ikm = shared_secret,
  salt = "nip44-v2",
  info = ""
)
```

Implementations MUST follow the NIP-44 v2 spec exactly:
https://github.com/nostr-protocol/nips/blob/master/44.md

### 3. Encryption

```
nonce = random_bytes(32)
message_keys = HKDF-SHA256(conversation_key, nonce, "encryption")
chacha_key   = message_keys[0:32]
chacha_nonce = message_keys[32:44]
hmac_key     = message_keys[44:76]

ciphertext = ChaCha20(plaintext, chacha_key, chacha_nonce)
mac        = HMAC-SHA256(hmac_key, nonce || ciphertext)
payload    = base64(version(1 byte) || nonce || ciphertext || mac)
```

This is NIP-44 v2 verbatim. Implementations MUST use an existing
audited NIP-44 library rather than rolling their own crypto.
Recommended: `@noble/ciphers` + `@noble/secp256k1` (MIT, audited).

### 4. Job creation flow

#### 4.1 Provider selection before encryption

The consumer MUST know the provider's pubkey before encrypting.
This requires a two-step flow:

**Step 1** — Consumer calls `GET /api/chat/provider` (new endpoint):
```json
{
  "modelName": "qwen2.5:7b",
  "minTrustTier": "public"
}
```
Returns:
```json
{
  "providerId": "uuid",
  "providerPubkey": "npub...",
  "model": "qwen2.5:7b"
}
```
This endpoint runs `pickChatProvider` and reserves the provider
for 30 seconds (to prevent TOCTOU between selection and job
creation). The reservation MUST be a short-lived lock in the
job-input cache (IPIP-0025 §1).

**Step 2** — Consumer encrypts `messages` using NIP-44 with
the provider's pubkey, then POSTs to `/api/chat`:
```json
{
  "providerId": "uuid",
  "clientPubkey": "npub...",
  "encryptedMessages": "<nip44 payload>",
  "modelName": "qwen2.5:7b",
  "maxTokens": 512,
  "temperature": 0.7
}
```

#### 4.2 Server stores ciphertext

`createChatJob` MUST store `encryptedMessages` verbatim in
`input_spec.encrypted_messages`. It MUST NOT decrypt it.
`input_spec.messages` MUST be omitted when E2E encryption is used.

The `client_pubkey` MUST be stored in `jobs.client_pubkey` so
the provider can derive the shared secret.

#### 4.3 Backwards compatibility

If `encryptedMessages` is absent and `messages` is present, the
job is treated as a legacy unencrypted job. Providers MAY continue
to accept that format for non-browser API clients during migration.
The browser chat MUST send only encrypted jobs to P2P providers. It
MUST fail closed if provider selection, key validation, or encryption
fails; it MUST NOT retry or fall back to a plaintext P2P job.

### 5. Provider daemon flow

When the daemon claims an encrypted job:

1. Read `input_spec.encrypted_messages` and `jobs.client_pubkey`.
2. Derive shared secret: `ECDH(daemon_privkey, client_pubkey)`.
3. Decrypt messages using NIP-44.
4. Run inference on plaintext messages (existing path).
5. For each token chunk, encrypt using the same shared secret
   before writing to `job_events`:
   ```json
   { "encrypted_text": "<nip44 payload>" }
   ```
   instead of the current:
   ```json
   { "text": "..." }
   ```
6. On job completion, write encrypted `done` event:
   ```json
   { "encrypted_text": "<nip44 payload of full response>" }
   ```

The daemon MUST NOT log decrypted message content. Existing
sanitize-stream logic (IPIP-0024) MUST run on decrypted text
before it is used but the sanitized output MUST be re-encrypted
before storage.

### 6. Consumer decryption (browser)

The browser's SSE handler detects `encrypted_text` on token events
and decrypts using the same NIP-44 shared secret before appending
to the message buffer:

```js
es.addEventListener("token", (e) => {
  const data = JSON.parse(e.data);
  const text = data.encrypted_text
    ? nip44.decrypt(conversationKey, data.encrypted_text)
    : data.text;
  appendToken(text);
});
```

The `conversationKey` MUST be held in JavaScript module scope
(not `localStorage`) for the duration of the session and dropped
on page unload.

### 7. Heartbeat advertisement

Every provider marked `available` MUST advertise E2E support and the
protocol version it implements:

```json
{
  "e2e_capable": true,
  "e2e_version": "nip44-v2"
}
```

The CLI provider daemon MUST include these fields in every heartbeat.
The control plane MUST only return providers advertising
`e2e_capable: true` and `e2e_version: "nip44-v2"` from
`GET /api/chat/provider`. A model-specific key MUST be present when
the client requests a model-specific key; the control plane MUST NOT
infer E2E support from the presence of a Nostr public key alone.

### 8. UI indication

The chat UI MUST show a lock icon when E2E encryption is active:

```
🔒 End-to-end encrypted · Provider: <name>
```

If no E2E-capable provider is available, the UI MUST say the message
was not sent and wait for an upgraded provider:

```
⚠ No E2E-capable provider is available. Your prompt was not sent.
```

### 9. New endpoint: `GET /api/chat/provider`

```
GET /api/chat/provider?modelName=qwen2.5:7b&minTrustTier=public
```

Response:
```json
{
  "providerId": "uuid",
  "providerPubkey": "hex64",
  "model": "qwen2.5:7b",
  "reservedUntil": "<iso8601 +30s>"
}
```

Rate limited identically to `POST /api/chat`. If no provider is
available, returns 503 with the same body shape as today.

### 10. New `jobs` column: `client_pubkey`

```sql
alter table jobs
  add column if not exists client_pubkey text;
```

Stores the consumer's public key (hex, 64 chars) so the provider
can derive the shared secret. This field is not sensitive — it is
a public key by definition.

## Rationale

**Why NIP-44 and not Signal Protocol / X3DH?** Nostr keypairs
(secp256k1) are already present on both sides. NIP-44 is a
minimal, audited spec built on those keys. Signal Protocol
requires ratcheting state and a key server — significant added
complexity for a stateless inference request. NIP-44 is the
right tool for single-message ECDH (no forward secrecy needed
per-token since the session key changes per job).

**Why not TLS only?** TLS protects transit between browser and
Infernet server, and between Infernet server and Supabase. It
does NOT protect against the Infernet operator (they terminate
TLS). This IPIP protects against the Infernet operator.

**Why is the provider selection step separate from job creation?**
The consumer needs the provider's pubkey before encrypting. If
we select the provider inside `POST /api/chat` as today, the
server has to tell the client which provider was chosen AFTER
the job is created, and we can't encrypt the job at creation
time. The pre-selection step (with a 30s reservation) solves
this cleanly without a round-trip race.

**Why 30 second reservation?** Long enough for a browser to do
ECDH, encrypt, and POST. Short enough that a reservation DoS is
infeasible (can't hold all providers busy for long).

**Why not forward secrecy per token?** Each job is a single
session with one shared secret. If the key is compromised after
the job completes, that job's content is exposed. True forward
secrecy (new key per message) requires a Double Ratchet and
is overkill for a stateless inference session. Adding per-job
fresh ECDH (the `nonce` already in NIP-44 provides this within
a session) is sufficient.

**Performance:** ECDH on secp256k1 is ~0.1ms in software.
ChaCha20 encrypts at >1 GB/s. A 4096-token chat response (~16 KB
of text) encrypts/decrypts in ~0.01ms. No perceptible latency.
This is not Tor.

## Backwards compatibility

- Providers that don't advertise `e2e_capable` are not selected by
  browser chat until they upgrade.
- Clients that don't send `encryptedMessages` are served by the
  existing path only on non-browser API routes during migration.
- `jobs.client_pubkey` is a nullable column — existing rows are
  unaffected.
- The new `GET /api/chat/provider` endpoint is additive.

Browser chat requires E2E for P2P providers. Legacy provider daemons
are filtered from browser chat until they upgrade and advertise NIP-44
support; non-browser API compatibility remains available during rollout.

## Reference implementation

- `apps/web/app/api/chat/provider/route.js` — new pre-selection endpoint
- `apps/web/lib/data/chat.js` — `createChatJob` stores `client_pubkey` + `encrypted_messages`
- `apps/web/app/chat/chat-view.js` — ECDH key generation, NIP-44 encrypt/decrypt, lock UI
- `apps/cli/lib/chat-executor.js` — NIP-44 decrypt input, encrypt output tokens
- `apps/cli/lib/node-client.js` — pass `client_pubkey` to event posts
- `supabase/migrations/<ts>_e2e_chat.sql` — `jobs.client_pubkey` column

## Test plan

### Unit

- NIP-44 round-trip: `encrypt(key, plaintext)` → `decrypt(key, ciphertext)` === `plaintext`.
- ECDH symmetry: `ECDH(a_priv, b_pub)` === `ECDH(b_priv, a_pub)`.
- `GET /api/chat/provider` returns provider pubkey and reserves the slot.
- Job creation with `encryptedMessages` stores ciphertext, no plaintext in `input_spec`.

### Integration

- Browser generates ephemeral keypair, encrypts prompt, job completes,
  browser decrypts tokens. Verify `job_events.data` contains no
  plaintext prompt or response words.
- Legacy provider (no `e2e_capable`) is excluded and the UI confirms
  the prompt was not sent.
- Reservation expiry: provider slot released after 30s if job not created.

### Security

- Verify decrypting with the wrong private key throws / returns garbage.
- Verify stored `job_events.data.encrypted_text` is not readable as
  plaintext by anyone with only the Supabase service key.

## Security considerations

- The browser's ephemeral private key exists only in JavaScript heap
  for the session duration. It is NOT persisted to localStorage or
  IndexedDB. A browser XSS attack can steal it — the same threat
  model as any in-browser crypto. Content Security Policy MUST be
  set on `/chat` to mitigate XSS.
- The provider reads plaintext during inference and could log it.
  This is mitigated by provider reputation (IPIP-0007) and TEE
  attestation (IPIP-0026 Phase 3), not by this IPIP.
- The pre-selection endpoint reveals which provider was selected
  before the job is created. This leaks the provider choice to
  anyone observing the API. Acceptable — provider assignment is
  already visible in the `jobs` table.
- NIP-44 does not provide sender authentication (only secrecy).
  A MITM who intercepts the `GET /api/chat/provider` response and
  substitutes their own pubkey would be able to decrypt. The
  control plane MUST sign the provider pubkey in the response
  using its DID key (IPIP-0007) to prevent this.

## Privacy considerations

After this IPIP, assuming both sides use it:
- Infernet operator: sees `client_pubkey`, `provider_id`, model,
  timing, token count — but NOT message content.
- Supabase: sees same metadata + ciphertext only.
- Network observers: see TLS-encrypted HTTPS only.
- The assigned provider: sees full plaintext (unavoidable for inference).
- Other providers: see nothing.

This is the strongest content privacy achievable without TEE hardware.

## Open questions

- Should the browser client cache the ephemeral keypair in
  `sessionStorage` to survive page refreshes within a session,
  or generate a fresh pair per conversation?
- Should authenticated users (with a persistent Nostr identity
  from IPIP-0003) use their account keypair instead of an
  ephemeral one, enabling cross-device conversation history that
  only they can decrypt?
- Should the provider sign their attestation of the session key
  (proving the response came from the correct provider) to
  prevent a control-plane MITM from swapping responses?
- At what adoption threshold should E2E encryption become the
  default (i.e., unencrypted jobs are rejected unless the client
  explicitly opts out)?
